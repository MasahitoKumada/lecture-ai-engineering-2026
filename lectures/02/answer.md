## 1. 宿題（基礎課題）：パラメータ変更の実験結果

エポック数（`num_train_epochs`）を元々の **20** から **10** に変更して再学習を行い、結果を比較しました。

| 項目 | 変更前の設定 (20 Epochs) | 変更後の設定 (10 Epochs) |
| :--- | :---: | :---: |
| **エポック数** | 20 | 10 |
| **形式遵守率 (`format_rate`)** | 9.5% -> 100.0% | 9.5% -> 100.0% |
| **内容正解率 (`content_rate`)** | 0.0% -> 85.7% | 0.0% -> 81.0% |
| **学習時間** | 約 240 秒 (4分) | 36.9 秒 |

### 考察と分析
- **形式遵守に対する影響**:
  エポック数を 10 に減らした場合でも、形式遵守率は **100%** を維持できました。これにより、JSONフォーマットという「出力の構造」を真似るだけであれば、10エポック（わずか 20 ステップの学習）でも十分に獲得可能であることが分かります。
- **内容正解率への影響**:
  エポック数を減らしたことで、内容の正解率についてもほぼ維持、または若干の推移が見られる結果となりました。今回のタスクのデータ規模（14件）では、比較的早い段階でモデルがFAQデータベースから適切な語彙を引っ張ってくる関係性を学習できていると考えられます。

## 2. 宿題（実装課題）：独自題材での追加実験レポート

独自に作成した「受講環境・システム推奨スペックに関するFAQ（5項目）」を使用して、LoRAによる形式学習を行いました。

### 2.1 根拠なし質問（UNGROUNDED）の設計戦略
根拠なし質問（FAQ外の不適切な問い合わせ）は以下の視点で計12問を設計しました：
- **FAQ項目と境界が曖昧なもの**: 例えば「推奨OS」に対して「Windows 10の動作状況」を問うなど、部分的に被る語彙を持ちながら判断不可能なもの。
- **完全にFAQに欠けているリソース情報**: 「PCレンタル」「学割」「マイク/カメラの要否」「メモリ要件」など、受講環境としては関連するものの、提示されたFAQ内には全く手がかりが無いもの。
これにより、モデルが「単に語彙をマッチさせるだけでなく、FAQの記述と正確に照合して判断しているか」を検証しました。

### 2.2 実験結果

| 評価段階 | 形式遵守率 (`format_rate`) | 内容正解率 (`content_rate`) |
| :--- | :---: | :---: |
| **学習前 (Before)** | 100.0% | 57.1% |
| **学習後 (After)** | 100.0% | 85.7% |

### 2.3 考察
- 異なる語彙ドメイン（システム環境要件）でも、LoRA学習によって**形式遵守率100.0%**を獲得することが確認できました。
- 内容正解率については、学習前後で大幅に向上し、指示された通りFAQにない事項について正しく `needs_review: true` を応答できる割合が大幅に増加しました。これはLoRAが指定フォーマット(JSON)への出力パターンの最適化に非常に寄与することを示しています。

## 3. 宿題（発展課題）：用語集SFTモデルと検索メカニズムとの比較考察

用語集データ（`glossary_sft.jsonl`）を使用して指示微調整(LoRA)を実行した実験結果と、検索アーキテクチャ(RAGなど)との詳細比較についての考察レポートです。

### 3.1 実験結果の集計
- **学習時間**: 45.0 秒
- **学習前 形式遵守率**: 0.0%
- **学習前 内容正解率**: 0.0%
- **学習後 形式遵守率**: 100.0%
- **学習後 内容正解率**: 100.0%

### 3.2 SFT (Fine-Tuning) でモデルに知識・回答形式を学習させるメリット・デメリット

#### メリット
1. **回答スタイルの完全な統一**: `{"answer": ..., "needs_review": ...}`のような特定の厳格な出力スキーマ・フォーマットの再現や口調の制御において、非常に少量の計算リソース(LoRA)でも完全な遵守(100%)を容易に学習・適用可能。
2. **推論時の低レイテンシと簡潔さ**: 外部データベース接続、チャンク検索、ベクトルストア検索といったオーバーヘッドなしで、モデル単一のフォワードパスのみで即座に応答が可能。

#### デメリット
1. **知識の更新コストの高さ**: FAQや用語定義が1件更新・削除・追加されるたびに、データセットを再構成して再度ファインチューニングを行う必要があり、継続的・動的運用の負担が重い。
2. **幻覚（ハルシネーション）と断定の混入**: SFTは「知識」の絶対的な正否を記憶するよりも、応答の「文字パターンの流暢さ」の学習に最適化されやすいため、用語集に存在しない難解な質問に対しても、もっともらしい別定義から用語を繋ぎ合わせて「もっともらしく誤った断定」を行いやすい。

### 3.3 検索拡張生成 (RAG) のメリット・デメリット

#### メリット
1. **動的な知識ソース更新の容易性**: 外部テキストDBの書き換えやベクトルDBのインデックス更新のみで、モデルに手を加えずに最新の情報・定義をベースとした回答を追従可能。
2. **根拠情報の可視化・監査性**: 回答が参照したドキュメントソースをメタデータ(URLや章番号)としてユーザーに提示可能であり、モデルが誤った回答をした際のデバッグやソース監査が極めて単純。

#### デメリット
1. **形式制御の不確実性**: JSONフォーマットなどの出力制御を100%保証するのが難しく、プロンプトの微細な変化に影響を受けてJSONパースエラーが発生しやすい。
2. **システム複雑性とコストの上昇**: ベクトルデータベース、エンベディングモデル、検索リランキングなど、インフラ構成が高度化し運用・金銭的コストが増加する。
